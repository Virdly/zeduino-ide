# Участие в разработке

Спасибо за интерес к ZedArduino IDE. Проект небольшой: ценится аккуратный, проверенный вклад без лишних зависимостей и «попутных» рефакторингов.

Перед PR прочитайте [ARCHITECTURE](docs/ARCHITECTURE.md), [BUILDING](docs/BUILDING.md) и [DEVELOPMENT](docs/DEVELOPMENT.md). Участвуя, вы соглашаетесь с [Кодексом поведения](CODE_OF_CONDUCT.md).

## 1. Как предложить изменение

1. Проверьте Issues и Discussions: возможно, проблема уже обсуждается.
2. Для крупной функции сначала создайте Issue/обсуждение с описанием сценария и плана — так вы не потратите время на подход, который не подходит проекту.
3. Форкните репозиторий и создайте ветку от `main`.
4. Внесите изменение, проверьте сборку, обновите документацию.
5. Откройте pull request по шаблону.

## 2. Ветки

```text
feat/<кратко>      новая функциональность
fix/<кратко>       исправление
docs/<кратко>      только документация
refactor/<кратко>  без изменения поведения
chore/<кратко>     сборка, зависимости, CI
```

Пример: `feat/board-favorites`, `fix/serial-port-busy`, `docs/build-mirror`.

Одна ветка — одна логическая задача. Не смешивайте переименование файлов, форматирование и функциональное изменение в одном PR.

## 3. Стиль коммитов

Conventional Commits, английский или русский — главное, чтобы сообщение было понятным:

```text
feat(editor): add include completion from project headers
fix(serial): stop monitor before opening upload port
docs(ai): document tool approval flow
chore(deps): update serialport to 13.0.0
```

Допустимые типы: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `build`, `ci`, `chore`. В теле коммита объясняйте «почему», если причина не очевидна. Ссылка на Issue — в теле (`Refs #12`, `Closes #34`).

## 4. Что проверить перед PR

- [ ] `npm install` проходит, `package-lock.json` не изменён без причины.
- [ ] `npm run typecheck` проходит.
- [ ] `npm run build` проходит; для изменений упаковки — `npm run package` и запуск `release\ZedArduinoIDE\ZedArduinoIDE.exe`.
- [ ] Нет `node_modules/`, `dist/`, `release/`, `artifacts/`, `settings.json`, ключей и личных путей в диффе.
- [ ] Нет настоящих API-ключей; в примерах только `sk-REPLACE_ME` и подобные заглушки.
- [ ] Новые строки интерфейса добавлены в `ru` и `en` (`src/renderer/i18n/*`); проверены обе локали.
- [ ] Проверены тёмная, светлая и кастомная темы; цвета только через CSS-переменные.
- [ ] UI не ломается при масштабе 0,7–1,5 и минимальном размере окна 960×600.
- [ ] Новый IPC-метод добавлен по цепочке `shared/types → shared/api → preload → main → store` (см. [DEVELOPMENT](docs/DEVELOPMENT.md#3-как-добавить-ipc-метод)).
- [ ] Файловые операции не выходят за корень проекта; внешние ссылки — только `http(s)`.
- [ ] Новая зависимость обоснована, её лицензия совместима с AGPL-3.0 и отражена в [THIRD-PARTY-NOTICES](THIRD-PARTY-NOTICES.md).
- [ ] Обновлена документация, если изменилось поведение, настройки, IPC или сборка.
- [ ] Для UI-изменений приложены скриншоты «до/после» (без ключей и личных данных).
- [ ] PR не содержит несвязанных изменений и массового переформатирования.

## 5. На что смотрят мейнтейнеры

| Критерий | Что проверяется |
| --- | --- |
| Польза | Решает заявленную проблему, не ломает существующие сценарии |
| Объём | Минимальный диф; нет попутных рефакторингов |
| Безопасность | Пути внутри проекта, нет shell-инъекций, ключи не логируются, внешние ссылки ограничены |
| Данные | Настройки и совместимость: старые `settings.json` не должны ломаться |
| Производительность | Автодополнение остаётся синхронным, индекс не растёт без лимитов, main не блокируется |
| UI/UX | Единые отступы, иконки, горячие клавиши, доступность (aria, фокус, Escape) |
| Локализация | Обе локали, без хардкода текста |
| Сопровождаемость | Типы вместо `any`, понятные имена, комментарии только по делу |
| Проверка | Typecheck/сборка, ручной сценарий в описании PR |

Мейнтейнер может попросить упростить решение или отложить его до версии, если оно тянет за собой архитектурные изменения.

## 6. Сообщения об ошибках

Используйте шаблон Issue (`.github/ISSUE_TEMPLATE/bug_report.yml`). Укажите:

- версию IDE (видна в «О программе» и в `package.json`);
- версию Windows (10/11, x64), версию `arduino-cli` (Настройки → Ардуино);
- плату и FQBN, порт/скорость (без серийных номеров, если они чувствительны);
- точные шаги воспроизведения и ожидаемое поведение;
- текст ошибки/вывод панели (можно скопировать кнопкой копирования);
- скриншот без ключей и личных путей.

Не прикладывайте `settings.json` целиком: там API-ключ. Не публикуйте уязвимости в Issues — см. [SECURITY](SECURITY.md).

## 7. Переводы

Интерфейс переключается между русским и английским в «Настройки → Основные». Строки лежат в `src/renderer/i18n/`:

- `common.ts` — общие кнопки/статусы;
- `shell.ts` — оболочка, панели, монитор;
- `dialogs.ts` — настройки, платы, библиотеки, темы;
- `ai.ts` — чат и инструменты;
- `editor.ts` — редактор, поиск, секции автодополнения.

Правила:

1. Добавляйте ключ сразу в `ru` и `en` одного и того же объекта.
2. Сохраняйте плейсхолдеры `{name}`, `{count}`, `{error}` без изменений.
3. Не переводите названия технологий (`Arduino`, `FQBN`, `ZIP`, `serialport`) и команды CLI.
4. Проверьте длину строки: английский текст часто длиннее, попап не должен обрезаться.
5. Нативное меню приложения пока не локализовано — это известное ограничение, не дублируйте его строки в словари.

Для нового языка потребуется расширить тип `Lang`, `DEFAULT_SETTINGS.language`, валидацию в `src/main/settings.ts`, выбор языка в настройках и все словари. Обсудите это в Issue заранее.

## 8. Кодекс поведения

Проект следует [Contributor Covenant 2.1](CODE_OF_CONDUCT.md). Неуважительное поведение, травля и дискриминация не допускаются. О проблемах сообщайте приватно через GitHub Security Advisories или мейнтейнеру; публичные конфликты не разбираются в Issue.
